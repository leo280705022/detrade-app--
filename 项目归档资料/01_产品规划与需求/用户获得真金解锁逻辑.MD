## 1. 背景与目标

### 1.1 背景

平台在运营过程中会向用户赠送**真金（USDT 计价）**，场景包括：

| 场景编码 | 场景名称 | 典型赠送形态 |
|----------|----------|--------------|
| `REG` | 新手注册 | 固定金额（如 20U） |
| `ONBOARD` | 新手引导任务 | 任务阶梯奖励 |
| `ACTIVITY` | 活动送真金 | 活动配置金额 |
| `COMP_DEMO` | 交易大赛 Demo | 排名/参与奖励 |
| `COMP_LIVE` | 交易大赛 Live | 排名真金奖励 |
| `TASK` | 任务 | 任务完成奖励 |
| `INVITE` | 邀请好友 | 邀请人/被邀请人奖励 |
| `LOTTERY` | 周抽奖 | 随机金额 |

赠送真金必须防止：批量注册套现、充提套利、对敲刷量、假邀请、秒开秒平刷解锁。

### 1.2 目标

1. **统一资金属性**：所有赠送真金进入 `bonus_balance`，不可直接提现。
2. **可配置解锁**：提供 4 种解锁模板，场景绑定模板，后管可配参数。
3. **全局风控**：身份、链上、行为、提现 clawback 全链路限制。
4. **可运营**：后管支持场景模板、条件组件、限额、黑名单与告警。
5. **可核算**：每笔赠送可追踪发放、进度、解锁、回收、过期。

### 1.3 非目标

- 不定义具体活动文案与前端 UI 细节（可另出交互稿）。
- 不覆盖「优惠券 / 抵扣金 / 体验金」的独立体系（若与 bonus 混用，见 3.1 资金优先级）。

## 2. 术语与定义

| 术语 | 定义 |
|------|------|
| 赠送真金 / Bonus | 平台赠送的 USDT 计价资金，入 `bonus_balance` |
| 本金 / Cash | 用户充值及已解锁可提现资金，入 `cash_balance` |
| 解锁 | 将 bonus（或其一部分）从「不可提现」变为「可提现」的过程 |
| 释放 | 逐步解锁模板中，按周期将部分金额转为可提现的动作 |
| 激活 | 充值流水模板中，满足充值+流水后奖金变为可用/可解锁状态 |
| 有效交易 | 满足最小金额、最小持仓时长、非对敲等规则的交易，才计入解锁进度 |
| Grant | 单笔赠送记录（一笔发放一条 grant） |
| Clawback | 用户提现本金时，按规则回收未解锁 bonus |
| 关联账户组 | 设备/IP/资金同源或同去向判定为同一主体的账号集合 |

### 2.1 有效交易（全局默认，后管可改）

计入解锁进度的交易必须**同时**满足：

| 条件 | 默认值 | 说明 |
|------|--------|------|
| 交易类型 | 合约 / UpDown / HighLow / Spread / Tap / 预测等真实业务交易 | 不含内部划转、充提 |
| 单笔名义金额 | ≥ 1 USDT | 后管可配 |
| 持仓时长 | ≥ 60 秒 | 二元类按结算完成计 1 笔；合约按开平仓完整周期 |
| 非对敲 | 未被标记为 Self-Match / Coordinated Trading | 同设备/同 IP/同资金簇反向对锁不计入 |
| 非自成交 | 买卖方非同一用户或同一关联组 | |
| 使用资金 | 可用 cash 或 bonus 均可 | 亏损优先扣 bonus（见 3.2） |

**不计入进度：**

- 持仓不足最小时长
- 被风控标记的对敲/关联反向单
- Demo 账户交易（Live 奖励不得用 Demo 交易解锁，除非场景明确为 `COMP_DEMO`）
- 系统强制平仓若持仓时长未达标

## 3. 全局资金规则（Layer 0，全场景强制）

> 本章为平台硬规则。后管仅可微调参数（如倍数、限额），不可关闭资金属性隔离与 clawback 开关（clawback 可配置比例策略，默认开启）。

### 3.1 账户结构

| 字段 | 含义 | 可否提现 | 可否开仓 |
|------|------|----------|----------|
| `cash_balance` | 可提现本金/已解锁资金 | 是 | 是 |
| `frozen_balance` | 下单/提现冻结 | 否 | 否（已占用） |
| `bonus_balance` | 未解锁赠送真金合计 | **否** | **是** |
| `bonus_locked` | 仍处于锁定/待激活的奖金（可选细分） | 否 | 按模板：部分可交易 / 部分不可交易 |
| `coupon_balance` | 抵扣金（若有） | 否 | 按券规则 |

**原则：赠送真金永不直接进入 `cash_balance`。** 仅「解锁/释放成功」后，对应金额从 `bonus_balance` 转入 `cash_balance`。

### 3.2 开仓 / 平仓扣款顺序

| 动作 | 顺序 |
|------|------|
| 开仓占用保证金 | ① `bonus_balance` → ② `cash_balance`（若配置「bonus 优先」；默认开启） |
| 平仓亏损 | ① 优先扣减本次占用的 bonus 部分 → ② 再扣 cash |
| 平仓盈利 | 盈利金额进入 `cash_balance`；但若关联 grant 未完全解锁，**盈利提现仍受提现风控约束**（见 3.5） |

说明：

- 默认「亏损优先吃 bonus」：降低平台实付成本，同时让用户用奖金真实参与交易。
- 盈利进 cash 不代表可立刻全额提现：若用户仍有未解锁 bonus，提现触发 clawback / 人工审核规则。

### 3.3 多笔 Grant 并行规则

| 规则 | 说明 |
|------|------|
| 独立核算 | 每一笔赠送独立一条 `bonus_grants` 记录，独立进度、独立状态 |
| 进度归属 | 有效交易量默认按 **FIFO（先发放先推进）** 分摊到未完成 grant；后管可改为「按比例分摊」 |
| 解锁入账 | 单笔 grant 达到解锁条件后，仅该笔金额转入 cash |
| 上限 | 受「单用户累计 / 单日 / 全平台」赠送上限约束（见第 6 章） |

### 3.4 生命周期状态机

```text
Pending（待发放）
  → Active（已入 bonus，可交易或待激活）
  → Unlocking（解锁进行中，有部分进度/部分已释放）
  → Partially_Released（部分已转入 cash）
  → Fully_Released（全部解锁完成）
  → Clawed_Back（提现回收）
  → Expired（过期回收）
  → Revoked（风控/人工撤销）
```

状态迁移规则：

| 状态 | 可交易 | 可进入解锁进度 | 可提现（该笔） |
|------|--------|----------------|----------------|
| Pending | 否 | 否 | 否 |
| Active | 按模板 | 是 | 否 |
| Unlocking | 是 | 是 | 仅已释放部分 |
| Partially_Released | 是 | 是 | 已释放部分 |
| Fully_Released | — | — | 是（已在 cash） |
| Clawed_Back / Expired / Revoked | 否 | 否 | 否 |

### 3.5 提现 Clawback（强制）

**触发：** 用户发起提现，且账户存在状态为 Active / Unlocking / Partially_Released 的 grant。

**默认公式（后管可选策略）：**

```text
策略 A（比例回收，默认）：
  clawback_amount = remaining_bonus × (withdraw_cash_amount / max(available_cash_before_withdraw, 0.00000001))
  clawback_amount = min(clawback_amount, remaining_bonus)

策略 B（全额回收）：
  任意本金提现 → 未解锁 bonus 全部回收

策略 C（门槛豁免）：
  若用户有效累计交易量 ≥ 全局阈值（如 10,000U）→ 跳过 clawback
```

**用户侧交互：**

1. 提现确认页展示：`本次提现将回收 XX USDT 未解锁奖励，是否继续？`
2. 用户确认后：先执行 clawback 扣减 bonus → 再冻结 cash 走提现审核/链上打款。
3. 站内信/流水类型：`bonus_clawback`。

**与「奖金产生的盈利」关系：**

- 盈利已计入 cash 的部分，不因 clawback 自动扣回（避免客诉复杂度过高）。
- 但对**高风险用户**（关联簇、设备超限、短时大额提现），提现进入人工审核，可按滥用条款冻结利润（协议层支持，见第 10 章）。

### 3.6 过期回收

| 参数 | 默认 | 说明 |
|------|------|------|
| grant 有效期 | 自发放起 30 天 | 场景可覆盖 |
| 过期动作 | 未解锁余额全部回收 | 状态 → Expired |
| 已释放部分 | 不回收 | 已在 cash |
| 过期前提醒 | T-3 / T-1 站内信 | 可配 |

### 3.7 全局发放限额

| 限额项 | 默认值 | 说明 |
|--------|--------|------|
| 单笔赠送上限 | 500 USDT | 超限需审批流 |
| 单用户累计未解锁 bonus 上限 | 1,000 USDT | 超限新 grant 延迟发放或拒绝 |
| 单用户累计历史获赠上限 | 5,000 USDT | 含已解锁 |
| 单用户单日获赠上限 | 200 USDT | |
| 全平台单日赠送名义总额上限 | 50,000 USDT | 触达告警 + 可自动停发 |
| 单设备可领奖账号数 | 2 | 超限不发 |
| 同 IP 段(/24) 24h 领奖账号数 | 5 | 超限人工或停发 |

## 4. 解锁模板体系（Layer 1）

### 4.1 模板关系（强制约定）

| 约定 | 说明 |
|------|------|
| 一场景一主模板 | 每个赠送场景绑定 **1 个主解锁模板** |
| 禁止双硬门槛叠加 | 不可「成长权重 100% + 积分 100」同时作为硬条件（成长模板内部只保留一种达标方式） |
| 全局资金规则叠加 | 任意模板均叠加 Layer 0（bonus 隔离、有效交易、clawback、限额） |
| 身份风控前置 | 发放前过 Layer 2 身份/链上检查，不通过则 Pending/拒绝发放 |

### 4.2 模板清单

| 模板编码 | 名称 | 适用倾向 |
|----------|------|----------|
| `GROWTH` | 成长解锁 | 注册、新手路径 |
| `VESTING` | 逐步释放 | 抽奖、小额活动、促活 |
| `DEPOSIT_VOLUME` | 充值流水激活 | 充值相关活动、大赛奖金激活 |
| `COMBO` | 组合任务解锁 | 任务、邀请、运营活动（主推可配） |

## 5. 模板详细规格

### 5.1 模板 A：成长解锁 `GROWTH`

#### 5.1.1 目标

用一条清晰成长路径引导新用户完成「充值 → 交易 → 留存」，达标后**一次性解锁**该笔 grant。

#### 5.1.2 达标方式（二选一，后管配置 `growth_mode`）

| growth_mode | 规则 | 默认 |
|-------------|------|------|
| `WEIGHT` | 权重任务进度达到 100% 即解锁 | **默认** |
| `POINT` | 成长积分达到 `point_target`（默认 100）即解锁 | 可选 |

**禁止同时要求 WEIGHT 与 POINT 都达标。** 另一种可作为 App 内展示成就，不卡解锁。

#### 5.1.3 默认权重任务（`WEIGHT` 模式）

| 条件编码 | 条件 | 权重 | 判定规则 |
|----------|------|------|----------|
| `first_deposit` | 完成首充 | 30% | 任意一笔充值成功且金额 ≥ `min_first_deposit`（默认 10U） |
| `first_trade` | 完成首次真实交易 | 20% | ≥1 笔有效交易 |
| `volume_1000` | 累计有效交易量 ≥ 1000U | 30% | 自 grant 发放后累计（或账户终身，后管选 `scope`） |
| `active_3d` | 连续活跃 3 天 | 20% | 连续 3 个自然日（UTC 或业务时区）每天 ≥1 次登录或 ≥1 笔有效交易 |

进度 = 已完成条件权重之和；达到 100% → `Fully_Released`。

#### 5.1.4 默认成长积分表（`POINT` 模式）

| 行为 | 积分 | 次数上限 | 备注 |
|------|------|----------|------|
| 首次充值 | 20 | 1 | |
| 第二次充值 | 20 | 1 | 单笔 ≥ 配置门槛 |
| 完成首笔有效交易 | 10 | 1 | |
| 累计有效交易量 1000U | 15 | 1 | |
| 累计有效交易 20 笔 | 10 | 1 | |
| 连续登录 5 天 | 10 | 1 | |
| 邀请 1 名有效用户 | 20 | 可配上限 | 有效用户定义见邀请场景 |
| 获取任意一次排行榜奖励 | 20 | 1 | |

`point_target` 默认 100；积分可超过 100，达到即解锁。

#### 5.1.5 节点顺序（可选）

| 参数 | 默认 | 说明 |
|------|------|------|
| `enforce_sequence` | false | 为 true 时必须按配置顺序完成 |
| 默认顺序（若开启） | 首充 → 首交 → 交易量 → 活跃 | 未完成前置则后续不计进度 |

**产品建议：默认关闭顺序强制**，避免与积分/多路径冲突导致完成率过低。

#### 5.1.6 注册赠送默认示例

| 参数 | 值 |
|------|-----|
| 场景 | `REG` |
| 金额 | 20 USDT |
| 模板 | `GROWTH` + `WEIGHT` |
| 有效期 | 30 天 |
| 解锁后 | 全额转入 cash |

#### 5.1.7 风控补充

- 发放前：设备/IP/黑名单检查。
- 进度中：无效交易不计。
- 提现：未解锁期间 clawback 生效。

### 5.2 模板 B：逐步释放 `VESTING`

#### 5.2.1 目标

小额奖金按天释放，拉长活跃；交易日可加速，防止躺平白拿。

#### 5.2.2 核心参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `daily_release_rate` | 10% | 按 grant 原始金额比例 |
| `total_days` | 10 | 理论最长释放天数（无加速） |
| `boost_enabled` | true | 是否允许交易日翻倍 |
| `boost_multiplier` | 2 | 满足条件时当日释放倍数 |
| `boost_min_volume` | 1 USDT | 当日有效交易量下限 |
| `boost_min_trades` | 3 | 当日有效交易笔数下限 |
| `no_trade_day_policy` | `half` | `full` 仍释放 / `half` 半速 / `zero` 不释放 |
| `timezone` | 业务时区（如 UTC+8） | 按自然日切日 |

#### 5.2.3 释放计算

```text
base_daily = grant_amount × daily_release_rate

当日应释放:
  if 当日有效交易量 ≥ boost_min_volume AND 当日有效笔数 ≥ boost_min_trades:
      day_amount = base_daily × boost_multiplier
  else if no_trade_day_policy == half:
      day_amount = base_daily × 0.5
  else if no_trade_day_policy == zero:
      day_amount = 0
  else:
      day_amount = base_daily

day_amount = min(day_amount, remaining_locked)
释放后 remaining_locked 减少，等额进入 cash_balance
```

#### 5.2.4 示例

- 获得 20U，10%/天，无加速：约 10 天释放完。
- 每天均满足 ≥1U 且 3 笔有效交易：约 5 天释放完（10%×2）。
- 连续无交易且 `no_trade_day_policy=zero`：暂停释放直至有交易或过期回收。

#### 5.2.5 风控补充

| 风险 | 控制 |
|------|------|
| 用 1U×3 笔刷翻倍 | 提高 `boost_min_volume`（建议场景默认 10U）或要求持仓时长 |
| 多账号领奖后躺平 | `no_trade_day_policy=zero` + 过期回收 |
| 释放后立即提现 | 仍叠加全局提现风控；可选「释放后 T+1 可提」 |

**默认建议（抽奖等）：** `boost_min_volume=10U`，`no_trade_day_policy=zero`，防止羊毛党用极小仓刷加速。

### 5.3 模板 C：充值流水激活 `DEPOSIT_VOLUME`

#### 5.3.1 目标

用户需充值并完成指定流水后，奖金才激活/解锁，防止纯领奖不入金。

#### 5.3.2 状态细分

```text
Active_Locked（已到账但不可交易/或可交易不可提现，由 trade_before_unlock 控制）
  → Active_Trading（可选：可交易）
  → Fully_Released（充值+流水均达标）
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `require_deposit_amount` | = 奖金金额 | 需完成的充值金额（可固定/等额/比例） |
| `deposit_scope` | 发放后新充值 | 是否允许历史充值抵扣：默认否 |
| `volume_base` | `bonus_plus_deposit` | `bonus_only` / `deposit_only` / `bonus_plus_deposit` |
| `volume_multiplier` | **10** | 流水倍数（**默认 10，不再使用 1**） |
| `required_volume` | volume_base × volume_multiplier | |
| `trade_before_unlock` | true | 未达流水前是否允许用 bonus 开仓 |

#### 5.3.3 默认档位表示例

| 奖金 | 需充值 | 流水基数 | 倍数 | 需流水 |
|------|--------|----------|------|--------|
| 20U | 20U | 40U | 10 | **400U** |
| 50U | 50U | 100U | 10 | **1,000U** |
| 100U | 100U | 200U | 10 | **2,000U** |

> 相对原 1 倍流水，默认 10 倍才能覆盖获客成本与套利空间。后管可按活动降到 5 或升到 15–20。

#### 5.3.4 激活判定

```text
deposit_ok = (grant 发放后累计充值 ≥ require_deposit_amount)
volume_ok  = (grant 关联有效交易量 ≥ required_volume)
if deposit_ok AND volume_ok → Fully_Released
```

#### 5.3.5 风控补充

- 充值来源若命中「资金同源簇」，grant 冻结待审。
- 流水仅计有效交易。
- 提现 clawback：未解锁前本金提现按策略回收奖金。

### 5.4 模板 D：组合任务解锁 `COMBO`（主推可配模板）

#### 5.4.1 目标

后管从条件组件库勾选条件，配置「完成任意 N 项」或「完成全部」，支持一次性解锁或按比例解锁。

#### 5.4.2 配置结构

```text
combo_config = {
  conditions: [ Condition, ... ],   // 勾选的条件列表
  logic: "ANY_N" | "ALL",           // 任意 N 项 / 全部
  n: 3,                             // logic=ANY_N 时必填
  unlock_style: "ALL_AT_ONCE" | "PRO_RATA",
  // PRO_RATA：每完成 1 个条件解锁 grant_amount / 所需项数
}
```

#### 5.4.3 条件组件库

| 条件编码 | 名称 | 可配参数 | 判定说明 |
|----------|------|----------|----------|
| `first_deposit_amt` | 首充金额 | `min_amount` | 首笔或任意一笔达门槛（可配） |
| `deposit_count` | 充值次数 | `count`, `min_each` | |
| `deposit_sum` | 累计充值 | `sum` | 支持阶梯：多档多条件 |
| `trade_volume` | 累计有效交易量 | `volume` | |
| `trade_count` | 累计有效交易笔数 | `count` | |

#### 5.4.4 示例：注册任务奖励 10U

```text
满足以下任意 3 项即可全部解锁：
☑ 首充 ≥ 20U
☑ 累计交易 1000U
☑ 累计 20 笔
☑ 连续交易 3 天
☑ 邀请 1 位好友首充
☑ 分享 1 次 Twitter
☑ 完成排行榜
logic = ANY_N, n = 3, unlock_style = ALL_AT_ONCE
```

#### 5.4.5 按比例解锁 `PRO_RATA`

```text
need = (logic==ALL ? conditions.length : n)
每完成 1 个「计入」的条件：
  release = grant_amount / need
  已计入条件数达到 need → 剩余尾差一并释放
```

注意：同一条件只计 1 次；互斥组内多选只计 1 次（后管可配 `mutex_group`）。

#### 5.4.6 风控补充

- 社交分享类易刷：需绑定真实分享回调或人工抽检；高风险用户不计入。
- 邀请类必须「有效用户」定义（见 7.7）。
- 条件进度同样只认有效交易/真实充值。

## 6. 全局身份与行为风控（Layer 2）

### 6.1 发放前检查（Grant Gate）

按顺序执行，失败则不发放或进入人工：

| 顺序 | 检查项 | 默认策略 |
|------|--------|----------|
| 1 | 用户状态正常（非封禁/冻结） | 拒绝 |
| 2 | 黑名单（用户/设备/地址/IP） | 拒绝 |
| 3 | 单用户累计/单日/单笔限额 | 拒绝或降额 |
| 4 | 同 Device ID 领奖账号数 | ≤2，超出拒绝 |
| 5 | 同 IP 段 24h 领奖账号数 | ≤5，超出人工/拒绝 |
| 6 | VPN/代理高风险 | 标记；策略：拒绝 / 仅低额 / 人工 |
| 7 | 链上资金同源簇 | 冻结发放，人工或加强 KYC |
| 8 | 场景专属前置（如邀请需好友首充） | 按场景 |

### 6.2 设备与环境

| 规则 | 默认 |
|------|------|
| Device Fingerprint 采集 | Canvas / WebGL / Audio 等（或第三方 Fingerprint） |
| 同设备领奖上限 | 2 个账号 |
| 同设备注册上限（可选） | 3 个账号，超出禁止注册或禁止领奖 |
| 模拟器/改机特征 | 高风险标签，默认禁止领奖 |

### 6.3 链上关联

| 类型 | 规则 | 处置 |
|------|------|------|
| 资金同源 | 多账号充值来自同一非交易所热钱包父地址 | 簇内 bonus 冻结，要求加强 KYC 或撤销 |
| 资金同去向 | 多账号提现至同一地址 | 提现拦截 + 人工 |
| 快速分散归集 | 短时间多地址归集模式 | 提高 C-Score 风险分 |

### 6.4 对敲与刷量

| 规则 | 说明 |
|------|------|
| 同频反向 | 1 秒内同品种反向开仓（多账户）→ 关联 + 交易不计入解锁 |
| 同设备/IP 对锁 | 禁止计入；可限制双向持仓（bonus 仓） |
| 秒平 | 持仓 < 60s 不计入有效交易 |
| 刷笔数 | 组合模板「笔数」与 VESTING 加速均受有效交易约束 |

### 6.5 用户风险分 C-Score（提现侧）

| 分档 | 行为特征（示例） | 提现策略 |
|------|------------------|----------|
| 高 | 正常交易、有充值、持仓多样 | 自动提现 |
| 中 | 新户、大额奖金、进度异常快 | 延迟 / 小额自动大额人工 |
| 低 | 关联簇、只领奖秒提、对敲标签 | 强制人工 + 可冻盈利 |

## 10. 用户协议与合规要点（摘要）

平台协议需明确：

1. 赠送真金为营销奖励，平台有权设定解锁、回收、撤销条件。
2. 多账户、对敲、刷量、虚假邀请、资金归集等属滥用，可取消奖励并没收滥用所得。
3. 可疑提现可要求加强 KYC（含视频认证）。
4. 参与即视为接受本规格对应的活动规则与反作弊条款。

## 11. 用户可见文案要点（产品）

发放时必须告知：

- 奖金不可直接提现，需完成解锁条件。
- 提现本金可能导致未解锁奖金被回收。
- 有效期与当前进度入口（资产/奖励中心）。

提现时：

- 二次确认 clawback 金额。

过期前：

- T-3 / T-1 提醒。

## 13. 验收标准（产品/测试）

1. 任意场景发放的赠送真金均进入 `bonus_balance`，直接提现余额不增加。
2. 未满足模板条件前，对应金额不可提现。
3. 无效交易不增加解锁进度。
4. 提现触发 clawback 金额计算与提示正确，流水可查。
5. 过期自动回收剩余 bonus，已释放部分保留。
6. 同设备超限账号无法领取。
7. 多笔 grant FIFO 进度互不覆盖错乱。
8. 后管修改场景模板参数后，**新发放** grant 使用新参数；存量 grant 使用发放时快照。
9. Demo 交易不能推进 Live 真金 grant 进度。
10. 邀请自邀、同设备上下级不发奖。
