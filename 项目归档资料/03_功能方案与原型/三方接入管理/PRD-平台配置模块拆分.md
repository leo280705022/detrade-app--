# 产品需求文档（PRD）

## 平台配置模块拆分 - 第三方接入管理

***

## 1. 文档概述

### 1.1 文档目的

本文档描述 Detrade 平台管理后台"平台配置"模块的拆分方案，将当前集中的平台配置页面拆分为"申请表管理"和"配置管理"两个独立模块。

### 1.2 项目背景

目前 Detrade 平台支持第三方平台申请接入我们的交易玩法。当前的平台配置页面将所有信息（包括申请信息和API配置信息）集中在一个页面中，导致：

- 审批流程与配置管理混淆
- 不同角色操作权限不清晰
- 数据安全存在隐患（API密钥与申请信息暴露在同一视图）

### 1.3 目标用户

| 角色     | 描述                     |
| ------ | ---------------------- |
| 运营审批人员 | 审核第三方平台的接入申请           |
| 平台管理员  | 管理已审批通过平台的配置信息，包括API密钥 |
| 系统管理员  | 拥有所有权限，可进行所有操作         |

***

## 2. 需求分析

### 2.1 当前状态（AS-IS）

**菜单结构：**

```
系统管理
  └── 平台配置（一个页面，包含所有信息）
```

**当前页面包含的数据字段：**

- 基本信息：ID、平台名称、平台类型、国家、目标市场、用户量、状态
- 联系信息：法律资格、平台联系人、邮箱、Telegram
- 技术配置：Domain URL、平台网址、IP白名单、API Key、Public Key、Private Key
- 操作：编辑、禁用/启用、重置密钥对

### 2.2 目标状态（TO-BE）

**菜单结构：**

```
系统管理
  ├── 申请表管理（新增 - 审批管理）
  ── 配置管理（原平台配置拆分 - 技术配置）
```

### 2.3 核心拆分逻辑

| 维度       | 申请表管理                   | 配置管理                             |
| -------- | ----------------------- | -------------------------------- |
| **数据范围** | 待审批、已拒绝的申请记录（审批通过后自动移除） | 已批准的平台配置                         |
| **主要功能** | 审批申请、查看申请详情、拒绝申请        | 配置管理、密钥管理、启用/禁用、配置状态管理           |
| **核心操作** | 通过（转移至配置表）、拒绝、查看详情      | 编辑配置、禁用/启用、重置密钥对、查看申请详情          |
| **敏感信息** | 不包含API密钥                | 包含API Key、Public Key、Private Key |

| 字段名      | 说明                          | 展示方式         |

| 平台名称     | 申请平台名称                      | 文本           |

| 用户量      | 100-500 / 1000-10000        | 文本           |

- **通过**：对"待审批"状态的申请进行审批通过操作，通过后自动向申请方邮箱发送审批通过邮件
- **拒绝**：对"待审批"状态的申请进行拒绝操作，拒绝后自动向申请方邮箱发送拒绝邮件

#### 3.1.4 审批流程

**通过流程：**

1. 运营人员点击"通过"按钮
2. 弹出确认弹窗："是否批准该平台接入？"
3. 确认后，系统自动执行以下操作：
   - 该申请记录从"申请表管理"中移除
   - 系统自动在"配置管理"中生成对应的配置记录，初始配置状态为"待配置"，平台状态为"禁用"
   - ~~系统自动向申请表中的邮箱地址发送审批通过邮件通知~~ **（暂缓：邮件发送功能后续补充）**
4. **弹出提示弹窗："审批成功，请前往配置管理进行配置"**，并提供"立即前往"按钮，点击后跳转至配置管理页面
5. 平台管理员在"配置管理"中完成API密钥等配置并保存后，配置状态变更为"已配置"，平台状态保持"禁用"
6. 配置完成后，平台管理员点击"启用"按钮，平台状态变更为"启用"，此时第三方平台正式接入

**拒绝流程：**

1. 运营人员点击"拒绝"按钮
2. 弹出拒绝原因输入框
3. 输入拒绝原因后确认
4. 申请状态变更为"已拒绝"
5. ~~系统自动向申请表中的邮箱地址发送拒绝邮件通知，包含拒绝原因~~ **（暂缓：邮件发送功能后续补充）**

#### 3.1.5 邮件通知机制（暂缓）

> **⚠️ 暂缓说明：** 邮件发送功能将在后续版本中补充实现，当前版本暂不实现。

审批通过和拒绝操作均需向申请方发送邮件通知，实现反向触达。

**触发条件：**

| 操作   | 触发时机      | 收件人       | 邮件模板     |
| ---- | --------- | --------- | -------- |
| 审批通过 | 运营人员确认通过后 | 申请表中的邮箱地址 | 审批通过通知模板 |
| 拒绝申请 | 运营人员确认拒绝后 | 申请表中的邮箱地址 | 拒绝通知模板   |

**邮件发送规则：**

- 邮件发送为异步操作，不阻塞审批流程
- 若邮件发送失败，系统记录失败日志并支持手动重发
- 邮件发送状态可在操作日志中查看

## 4. 数据流转设计

### 4.1 申请到配置的数据流转

```
┌─────────────┐    审批通过    ┌─────────────┐
│  申请表管理  │ ────────────> │  配置管理    │
│             │               │             │
│ 待审批       │               │ 已批准平台   │
│ 已通过       │               │ 的API配置    │
│ 已拒绝       │               │             │
└─────────────               └─────────────┘
```

### 4.2 状态映射

| 申请表状态 | 配置管理对应   | 说明                 |
| ----- | -------- | ------------------ |
| 待审批   | 无对应记录    | 等待审批               |
| 已通过   | 自动生成配置记录 | 状态为"禁用"，配置状态为"待配置" |
| 已拒绝   | 无对应记录    | 不予接入               |

## 7. 非功能需求

### 7.1 性能要求

- 列表加载时间 < 2秒
- 搜索响应时间 < 1秒
- 支持分页，每页默认20条

### 7.2 安全要求

- API密钥必须脱敏展示
- 私钥仅在新建/重置时完整展示一次
- 操作日志记录所有敏感操作
- IP白名单校验格式

### 7.3 兼容性要求

- 支持 Chrome 90+
- 支持 Safari 14+
- 支持 Firefox 88+
