# 比分展示标准化方案

**文档日期**: 2026-07-31  
**文档目的**: 解决不同运动类型比分展示差异大、维护成本高的问题，提出一套"一份代码、多运动适配"的标准化方案

---

## 一、问题分析

### 1.1 现状痛点

不同运动类型的比分展示存在显著差异，主要体现在：

| 运动类型 | 比分格式 | 分节结构 | 时间展示 | 特殊元素 |
|---------|---------|---------|---------|---------|
| 足球 | 2-1 | 上半场/下半场 | 67'（分钟） | 红黄牌、加时 |
| 篮球（NBA） | 108-95 | Q1/Q2/Q3/Q4/OT | Q3 05:23 | 24秒进攻计时 |
| 网球 | 6-4, 3-6, 7-5 | Set1/Set2/Set3... | 局分（40-30） | 盘分 + 局分双层 |
| 棒球 | 3-2 | Inning1-Inning9 | Top/Bot + Inning | 局分 + 总分 |
| 冰球 | 4-3 | P1/P2/P3/OT | P2 12:45 | 节次 + 时间 |
| 综合格斗 | — | Round 1/2/3... | R2 03:22 | 回合数、KO/判定 |
| 拳击 | — | Round 1-12 | 回合进行中 | 回合数、判定 |

如果为每种运动单独开发展示组件，会导致：
- **代码冗余**：N 种运动 = N 套展示逻辑
- **维护成本高**：修改一个通用功能（如动画效果）需要改 N 个地方
- **一致性差**：不同运动的卡片风格、交互方式不统一
- **扩展困难**：新增运动类型需要从零开发

### 1.2 核心结论

经过对 Polymarket、Flashscore、ESPN、LiveScore 等平台的调研，**比分标准化在业界已有成熟的实践模式**——"通用数据模型 + 通用展示外壳 + 运动特定渲染策略"。核心思路是：**抽象出所有运动的共性结构，将差异点收敛到可配置的渲染策略中**。

## 二、方案设计

### 2.1 整体架构：三层分离

```
┌──────────────────────────────────────────────────────────┐
│  第三层：运动特定扩展（仅在详情页使用）                        │
│  FootballDetail / BasketballDetail / TennisDetail / ...  │
│  → 展示该运动的完整技术统计、事件时间线等                       │
├──────────────────────────────────────────────────────────┤
│  第二层：通用比分卡片组件（列表级，所有运动共享）                 │
│  ScoreCard                                                │
│  → 统一的布局结构：Logo + 名称 + 比分 + 状态 + 时间           │
│  → 通过 sportType 自动切换渲染策略                            │
│  → 可选叠加预测市场信息（概率/赔率）                            │
├──────────────────────────────────────────────────────────┤
│  第一层：统一数据模型（运动无关）                               │
│  UnifiedMatchData                                         │
│  → 所有运动共享同一份数据结构                                  │
│  → 数据源差异在防腐层抹平                                     │
└──────────────────────────────────────────────────────────┘
```

**关键原则**：列表级展示（事件卡片、Live 列表）只用第一层 + 第二层，完全通用；详情页才需要第三层的运动特定扩展。

### 2.2 第一层：统一数据模型

所有运动的比分数据，都可以映射到以下统一结构：

```typescript
interface UnifiedMatchData {
  // === 基础信息（所有运动通用） ===
  matchId: string;
  sportType: SportType;           // 'football' | 'basketball' | 'tennis' | 'baseball' | 'hockey' | 'mma' | ...
  league: {
    name: string;                 // "NBA" / "英超" / "ATP"
    logo?: string;
  };
  status: MatchStatus;            // 'scheduled' | 'live' | 'finished' | 'cancelled' | 'postponed'
  scheduledTime: string;          // ISO8601 开赛时间

  // === 参赛方（所有运动通用：主队vs客队 或 选手1vs选手2） ===
  competitors: [
    { id: string; name: string; logo?: string; side: 'home' },
    { id: string; name: string; logo?: string; side: 'away' }
  ];

  // === 比分（核心统一结构） ===
  score: {
    total: { home: number; away: number };    // 总比分/最终比分
    periods: PeriodScore[];                    // 分节/分局明细（运动特定含义）
  };

  // === 时间/进度（所有运动通用） ===
  matchTime: {
    display: string;              // "67'" / "Q3 05:23" / "Set 3" / "R2" — 直接用于展示的字符串
    isRunning: boolean;           // 计时器是否在跑
  };
}

interface PeriodScore {
  periodNumber: number;           // 第几节/第几局
  periodLabel: string;            // "Q1" / "1st Half" / "Set 1" / "Inning 5" — 直接用于展示
  homeScore: number;
  awayScore: number;
}
```

**设计要点**：

- `score.total` 是所有运动的"主比分"，足球是总进球、篮球是总得分、网球是总盘分、棒球是总得分。列表级展示只需要这个字段。
- `score.periods` 是分节明细，不同运动的 `periodLabel` 不同，但数据结构一致。用于卡片上的辅助展示。
- `matchTime.display` 是**预格式化的展示字符串**，由数据层根据运动类型生成，前端直接渲染，无需关心格式化逻辑。
- 数据源（Sportradar/LSports 等）的字段差异在**防腐层（Adapter）**中抹平，统一映射到上述 Schema。

### 2.3 各运动如何映射到统一模型

| 运动 | `score.total` | `score.periods` | `matchTime.display` | 映射说明 |
|------|-------------|-----------------|--------------------|---------| 
| 足球 | 总进球 2-1 | `[{1st Half, 1-0}, {2nd Half, 1-1}]` | `67'` | 直接映射 |
| 篮球 | 总得分 108-95 | `[{Q1, 28-22}, {Q2, 30-25}, ...]` | `Q3 05:23` | 直接映射 |
| 网球 | 总盘分 2-1 | `[{Set 1, 6-4}, {Set 2, 3-6}, {Set 3, 7-5}]` | `Set 3` | total=盘分，periods=每盘局分 |
| 棒球 | 总得分 3-2 | `[{Inning 1, 0-1}, {Inning 2, 2-0}, ...]` | `Bot 5th` | 直接映射 |
| 冰球 | 总进球 4-3 | `[{P1, 1-1}, {P2, 2-1}, {P3, 1-1}]` | `P2 12:45` | 直接映射 |
| 格斗 | 不适用（0-0 或空） | `[{R1, —}, {R2, —}]` | `R2 03:22` | total 无意义，以 period 信息为主 |

**关键洞察**：所有运动都能用 `{ total, periods[], time }` 三元组表达。差异仅在于 `periodLabel` 的命名和 `total` 的语义，但这些差异对前端展示是透明的——前端只需要"渲染数字"，不需要"理解数字的含义"。

### 2.4 第二层：通用比分卡片组件

列表级（Live 列表、Starting Soon、Upcoming）使用的通用卡片，所有运动共享同一套布局：

**卡片布局结构：**

```
┌─────────────────────────────────────────────────────┐
│  [联赛图标] 联赛名称              [状态标签] [时间]    │  ← 头部：联赛 + 状态
├─────────────────────────────────────────────────────┤
│                                                      │
│  [主队Logo]  主队名称    2 - 1    客队名称  [客队Logo] │  ← 主体：比分（核心区域）
│                                                      │
│  (可选) Q1: 1-0  Q2: 1-1  Q3: 0-0                   │  ← 辅助：分节小分（横向滚动）
│                                                      │
├─────────────────────────────────────────────────────┤
│  [Yes 65¢]  [No 35¢]              交易量 $128K       │  ← 底部：预测市场信息
└─────────────────────────────────────────────────────┘
```

**组件代码结构：**

```
ScoreCard/                       # 通用比分卡片
├── ScoreCard.tsx                # 容器组件，接收 UnifiedMatchData
├── components/
│   ├── MatchHeader.tsx          # 联赛名 + 状态标签 + 时间（通用）
│   ├── ScoreBody.tsx            # 队名/选手名 + 比分数字（通用）
│   ├── PeriodScores.tsx         # 分节小分横向展示（通用，数据驱动）
│   └── MarketStrip.tsx          # 预测市场概率/赔率条（通用）
├── hooks/
│   ├── useLiveScore.ts          # WebSocket 实时比分订阅
│   └── useScoreAnimation.ts     # 比分变化时的闪烁动画
└── styles/
    └── ScoreCard.css            # 统一样式 + CSS 变量主题
```

**核心渲染逻辑（伪代码）：**

```typescript
function ScoreCard({ match }: { match: UnifiedMatchData }) {
  return (
    <div className="score-card">
      {/* 头部：所有运动完全一致 */}
      <MatchHeader 
        league={match.league} 
        status={match.status} 
        time={match.matchTime.display} 
      />
      
      {/* 主体：所有运动完全一致，比分就是数字 */}
      <ScoreBody 
        home={match.competitors[0]}
        away={match.competitors[1]}
        homeScore={match.score.total.home}
        awayScore={match.score.total.away}
      />
      
      {/* 分节小分：有数据就展示，没数据就隐藏，组件本身是通用的 */}
      {match.score.periods.length > 0 && (
        <PeriodScores periods={match.score.periods} />
      )}
      
      {/* 预测市场信息：所有运动完全一致 */}
      <MarketStrip markets={match.markets} />
    </div>
  );
}
```

**这套组件不需要按运动类型分支渲染。** 因为：
- 比分就是数字，`2-1` 和 `108-95` 的渲染逻辑完全一样
- 分节小分是数据驱动的，`periodLabel` 已经是格式化好的字符串
- 时间显示也是数据驱动的，`matchTime.display` 已经是格式化好的字符串

### 2.5 处理特殊情况的策略

有些运动的比分结构确实比较特殊（如网球的双层比分、格斗的无总分），处理策略如下：

| 特殊情况 | 处理策略 | 示例 |
|---------|---------|------|
| 网球双层比分（盘分 + 局分） | `total` 存盘分，`periods` 存每盘局分，卡片主体显示盘分，辅助区显示最近盘的局分 | total: 2-1, periods: [{Set 1, 6-4}, {Set 2, 3-6}, {Set 3, 4-3}] |
| 格斗无总分 | `total` 设为 0-0 或不展示，主体区域显示"R2 03:22"代替比分 | 通过 status + matchTime 组合展示 |
| 棒球 inning 展示 | `periods` 数组可能很长（9-12 局），辅助区做横向滚动，只显示最近 3 局 | 前端限制显示数量 + 横向滚动 |
| 加时/点球大战 | 追加 period 条目，`periodLabel` 标记为 "OT" / "PEN" | periods: [..., {OT, 1-0}] |

**原则**：特殊情况的处理逻辑放在**数据适配层**（生成 UnifiedMatchData 的地方），不放在前端组件里。前端组件始终是"给什么数据就渲染什么数据"。

## 三、数据适配层设计

### 3.1 防腐层（Adapter）的作用

不同数据源（Sportradar、LSports、自有数据服务等）的字段命名和结构各不相同，必须通过适配层统一：

```
数据源 A (Sportradar)  ──┐
数据源 B (LSports)     ──┼──→  Adapter  ──→  UnifiedMatchData  ──→  ScoreCard
数据源 C (自有服务)     ──┘
```

### 3.2 适配器示例

```typescript
// 适配器接口
interface ScoreDataAdapter {
  normalize(raw: any): UnifiedMatchData;
}

// Sportradar 适配器
class SportradarAdapter implements ScoreDataAdapter {
  normalize(raw: SportradarPayload): UnifiedMatchData {
    return {
      matchId: raw.sport_event.id,
      sportType: this.mapSportType(raw.sport_event.sport),
      league: { name: raw.sport_event.sport_event_context.tournament.name },
      status: this.mapStatus(raw.sport_event.status.state),
      scheduledTime: raw.sport_event.scheduled,
      competitors: [
        { id: raw.sport_event.competitors[0].id, name: raw.sport_event.competitors[0].name, side: 'home' },
        { id: raw.sport_event.competitors[1].id, name: raw.sport_event.competitors[1].name, side: 'away' }
      ],
      score: {
        total: { 
          home: raw.sport_event_status.home_score, 
          away: raw.sport_event_status.away_score 
        },
        periods: (raw.sport_event_status.period_scores || []).map(p => ({
          periodNumber: p.number,
          periodLabel: p.name,         // Sportradar 已格式化："1st Half", "Q1" 等
          homeScore: p.home_score,
          awayScore: p.away_score
        }))
      },
      matchTime: {
        display: this.formatTime(raw.sport_event_status),  // 根据运动类型格式化
        isRunning: raw.sport_event_status.clock === 'running'
      }
    };
  }
}
```

**适配器的核心价值**：前端组件永远只对接 `UnifiedMatchData`，换数据源只需要新增一个 Adapter，不动前端代码。

## 四、实时数据更新方案

### 4.1 WebSocket 差分推送

比分更新采用差分推送模式，只推送变化的字段，减少数据传输量：

```typescript
interface ScoreUpdate {
  matchId: string;
  diff: {
    score?: { total?: { home?: number; away?: number }; periods?: PeriodScore[] };
    matchTime?: { display?: string; isRunning?: boolean };
    status?: MatchStatus;
  };
  timestamp: number;    // 用于排序
  sequence: number;     // 序列号，防止乱序
}
```

### 4.2 前端更新逻辑

```typescript
// 通用的比分更新 Hook，所有运动共用
function useLiveScore(matchId: string): UnifiedMatchData {
  const [match, setMatch] = useState<UnifiedMatchData>(initialData);
  
  useEffect(() => {
    const ws = subscribeScoreUpdates(matchId, (update: ScoreUpdate) => {
      setMatch(prev => ({
        ...prev,
        score: update.diff.score 
          ? { ...prev.score, ...mergeScore(prev.score, update.diff.score) }
          : prev.score,
        matchTime: update.diff.matchTime 
          ? { ...prev.matchTime, ...update.diff.matchTime }
          : prev.matchTime,
        status: update.diff.status ?? prev.status,
      }));
    });
    return () => ws.unsubscribe();
  }, [matchId]);
  
  return match;
}
```

**这段 Hook 是运动无关的。** 不管足球还是网球，更新逻辑都是"合并 diff 到现有状态"。

## 五、方案对比与选择

### 5.1 三种可选方案

| 方案 | 描述 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **A. 完全统一** | 所有运动用完全相同的卡片布局，不做任何运动特定处理 | 代码量最少，维护最简单 | 网球等特殊运动的展示不够精细 | MVP 阶段、运动类型较少时 |
| **B. 通用外壳 + 策略模式**（推荐） | 列表级完全统一，详情级按运动类型扩展 | 兼顾统一性和灵活性 | 需要为特殊运动设计扩展点 | 中长期方案 |
| **C. 完全定制** | 每种运动独立开发展示组件 | 每种运动可以做到最优展示 | 代码量 N 倍，维护成本极高 | 不推荐 |

### 5.2 推荐方案：B — 通用外壳 + 策略模式

理由：
1. **列表级（Live/Starting Soon/Upcoming）完全统一**：这是用户看到最多的界面，统一后体验一致、代码量最小
2. **详情级允许运动特定扩展**：点击进入详情后，可以展示该运动的完整技术统计（如篮球的投篮命中率、足球的控球率等），这部分按运动类型分别实现
3. **扩展点清晰**：通过 `sportType` 字段路由到不同的详情渲染器，新增运动只需注册一个新的渲染器

## 六、实施路径

### 6.1 分阶段落地

| 阶段 | 内容 | 工作量 | 产出 |
|------|------|--------|------|
| **P0：数据模型统一** | 定义 UnifiedMatchData Schema，实现数据适配层 | 1-2 周 | 统一数据接口，所有运动数据可标准化输出 |
| **P1：通用卡片组件** | 开发 ScoreCard 通用组件，覆盖列表级展示 | 1 周 | 一套卡片组件覆盖所有运动的列表展示 |
| **P2：实时更新接入** | 实现 WebSocket 差分推送 + useLiveScore Hook | 1 周 | 比分实时更新，所有运动共用同一套逻辑 |
| **P3：详情页扩展** | 按运动类型开发详情页（可逐步推进） | 每种运动 2-3 天 | 详情级的运动特定展示 |

### 6.2 新增运动类型的 Checklist

当需要支持一种新运动时，只需完成以下步骤：

- [ ] 在数据适配层新增该运动的映射规则（定义 total/periods/time 的映射逻辑）
- [ ] 在 SportType 枚举中注册新类型
- [ ] （可选）如需详情特定展示，新增一个 DetailRenderer 并注册到渲染器注册表

**列表级展示零改动。** 这是方案 B 的核心价值。

## 七、总结

| 维度 | 方案要点 |
|------|---------|
| **核心思路** | 通用数据模型 + 通用列表卡片 + 运动特定详情页 |
| **数据层** | UnifiedMatchData 统一 Schema，所有运动映射到 `{ total, periods[], time }` 三元组 |
| **组件层** | 列表级 ScoreCard 完全通用，运动差异通过数据驱动而非代码分支处理 |
| **适配层** | 防腐层抹平数据源差异，换数据源不动前端 |
| **实时层** | 差分推送 + 通用合并逻辑，运动无关 |
| **扩展成本** | 新增运动类型：数据层映射 + 注册类型枚举，列表级零改动 |
| **预估工作量** | P0-P2（通用方案）约 3-4 周，P3（详情扩展）按运动类型逐步推进 |
