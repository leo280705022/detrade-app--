## 一、需求解读与目标对齐

### 1.1 老板核心诉求提炼

从 SVG 架构图（"BCGame 融合 TG 交互逻辑图：永旺防封冗余 + TonPlay 合规矩阵"）中提炼出以下核心策略：

| 维度 | 策略 | 核心手段 |
|:---|:---|:---|
| **流量获取** | 双轨并行 | ① 永旺打法：投放马甲号 + 中性话术 + 可弃炮灰（防封冗余）<br>② TonPlay 打法：官方社媒矩阵 + KOL 联盟 + 玩家裂变 deep link |
| **转化钩子** | Bonus 开门炮 | 无存款奖 + 高额首充 + 每日返水 + gas-free + 无 KYC 即点即玩 |
| **信任背书** | 双锚点 | ① 认证频道 + 马甲热备（封了热切换）<br>② 合规牌照背书（Brazil 双牌照、KK 背书、provably fair） |
| **分发矩阵** | 一引擎八皮肤 | 多语言频道（Brazil/Mexico/CIS/日韩…）同结构复制 |
| **收口原则** | 唯一目的地 | 所有流量收到主 Bot，永不让主体直吃投放流量 |
| **转化漏斗** | Bot 内闭环 | 注册 → 首充 FTD → 留存复购，全部在 chat 内完成 |
| **客服裂变** | 独立分线 | 客服 Bot 与玩法 Bot 分离；晒单水群二次拉新 |
| **归因防封** | 全链中枢 | deep link 全链归因 + 三层冗余防封 + 分市场分号隔离 + 低质流量识别 |

### 1.2 用户明确方向

> 多频道引流到官方应用、多 Bot、红包、裂变、代理推广

> 目标是轻 App，打开快，不能有太多的 JS 和 CSS

**核心矛盾**：功能丰富 vs 极致轻量。这要求我们在架构上做"薄客户端 + 厚服务端"的取舍。

## 二、竞品 TG Mini App 对标分析

### 2.1 竞品速览

| 竞品 | 定位 | 核心亮点 | 可借鉴点 |
|:---|:---|:---|:---|
| **Storm Trade** | TON 链永续合约 | Squads 战队系统 + 排行榜竞争 | 社交战队 = 交易变公会战，裂变引擎 |
| **Blum** | 混合交易所 + Drop Game | "点点乐"游戏降低认知门槛 | 游戏化是 TG 生态的流量密码 |
| **Roach Racing Club** | 游戏化博弈 | 涨跌预测包装成"赛跑下注" | 消除金融严肃感，吸引非交易用户 |
| **Rush Trade** | 一键跟单/狙击 | 移动端极致简化，强调"快" | 速度是 TG Mini App 的生命线 |
| **Nadsa Arcade** | 预测市场街机化 | 80 年代街机 UI，红蓝对抗 | 视觉冲击力 = 传播力 |
| **ExpertOption** | 二元期权 | 图表实时显示他人买卖气泡 | 社交氛围营造，FOMO 驱动下单 |

### 2.2 关键洞察

1. **游戏化 > 金融化**：TG 用户对"玩游戏"的接受度远高于"做交易"，必须用游戏外衣包装金融内核
2. **社交 = 裂变引擎**：Storm Trade 的 Squad 系统证明，把交易变成团队竞赛，用户会自发拉人
3. **速度定生死**：TG Mini App 的加载速度直接影响转化率，3 秒是生死线
4. **极简交互**：二元期权平台（Quotex/ExpertOption）已证明，3 步内完成一笔交易是最佳体验

### 3.2 Bot 矩阵设计（多 Bot 策略）

| Bot 类型 | 数量 | 用途 | 用户感知 | 技术要点 |
|:---|:---|:---|:---|:---|
| **主 Bot** | 1 个 | 核心交易、注册、充提、游戏大厅 | DeTrade 官方 Mini App | 轻量级 SPA，< 200KB 总资源 |
| **红包 Bot** | 1 个 | 红包发放、裂变活动、任务奖励 | 福利中心 | 独立部署，可独立被封不影响主 Bot |
| **客服 Bot** | 1 个 | 工单、FAQ、人工转接 | 7×24 在线客服 | 与主 Bot 数据隔离 |
| **马甲 Bot** | N 个 | 投放引流第一跳，中性话术包装 | 加密货币资讯/学习社区 | 可弃炮灰，被封热切换到备用 |
| **活动 Bot** | 按需 | 临时活动（锦标赛、空投） | 限时活动入口 | 活动结束后可下线 |

**Bot 间协作流**：
```
马甲 Bot（引流第一跳，中性内容）
    ↓ 引导用户"了解更多"
主 Bot（DeTrade Mini App，交易核心）
    ↓ 完成任务/获胜后
红包 Bot（发放奖励，激发裂变）
    ↓ 用户遇到问题
客服 Bot（独立服务，不污染交易数据）
```

## 四、核心功能模块拆解

### 4.1 模块一：极速注册与即点即玩

**对标 SVG 架构**：⑤ 收口层 + ⑥ 转化漏斗

**设计原则**：无 KYC 即点即玩，压平 visit→reg 门槛

| 功能点 | 实现方式 | 优先级 |
|:---|:---|:---|
| Telegram 一键登录 | 利用 `tg.initData` 直接获取用户信息，无需手动填写 | P0 |
| 托管钱包自动创建 | 注册即创建非托管/托管钱包，用户无感知 | P0 |
| 体验金自动发放 | 新用户注册即送 USDT 体验金，直接可交易 | P0 |
| 渐进式 KYC | 提现时才触发 KYC，充值/交易无门槛 | P1 |

**技术方案**：
- 利用 Telegram WebApp API 的 `initData` / `initDataUnsafe`，在服务端验签后直接完成注册
- 前端仅需一个按钮 + 加载动画，整个注册流程零表单

### 4.2 模块二：核心交易（二元期权）

**对标竞品**：ExpertOption / Quotex 的极简交互

**设计原则**：3 步开单，5 秒内完成

```
选择标的 → 选择方向(涨/跌) → 确认金额 → 完成
```

| 功能点 | 说明 | 轻量化策略 |
|:---|:---|:---|
| 标的列表 | 热门币种，可搜索 | 虚拟列表，仅渲染可视区域 |
| K 线图 | 简化版，仅显示价格走势 | 使用 Canvas 绘制，不引入重量级图表库 |
| 开单面板 | 金额选择 + 方向按钮 | 纯 CSS 动画，无 JS 动画库 |
| 持仓列表 | 当前持仓 + 实时盈亏 | 仅轮询关键数据，非全量刷新 |
| 交易历史 | 近 50 条 | 分页加载，每次 20 条 |

**资源预算**：整个交易模块 HTML + CSS + JS 控制在 **100KB** 以内

### 4.3 模块三：红包系统（裂变引擎）

这是 TG 生态中最强的裂变工具，对标微信红包的社交传播力。

**红包类型**：

| 红包类型 | 触发场景 | 分发方式 | 裂变效果 |
|:---|:---|:---|:---|
| **新人红包** | 用户首次进入 Mini App | 自动发放体验金 | 降低首次交易门槛 |
| **拼手气红包** | 用户完成交易后 | 分享到群，N 人抢 | 群内传播，带 deep link 回流 |
| **口令红包** | 活动期间 | 输入口令领取 | 频道/群内传播口令 |
| **任务红包** | 完成指定任务 | 自动发放到钱包 | 引导用户行为 |
| **排位红包** | 排行榜/锦标赛 | 赛季结束发放 | 竞争激励，提升活跃 |

**技术实现**：
- 红包 Bot 独立部署，通过 `tg.sendData` 与主 Bot 通信
- 红包数据全在服务端，前端仅渲染领取状态
- 红包分享卡片使用 Telegram 的 `link_preview_options` 生成富媒体预览

### 4.4 模块四：代理推广系统

**对标现有系统**：DeTrade 联盟伙伴与邀请计划 V2

**TG 专属增强**：

| 功能 | 现有能力 | TG 增强 |
|:---|:---|:---|
| 推广链接 | 通用邀请链接 | 含 channel/bot 来源参数的 deep link |
| 代理后台 | Web 独立后台 | 增加 TG Bot 内轻量版看板 |
| 佣金结算 | 周结 | 增加 Bot 内实时佣金查询 |
| 素材支持 | 海报生成 | 增加 TG 专用贴纸/动图/视频素材 |
| 下级管理 | Web 后台 | Bot 内查看下级活跃状态 |

**归因链路**：
```
推广链接（含 agent_id + channel_id）
    → 用户点击 → Telegram deep link
    → 打开 Mini App → 服务端解析参数
    → 注册时绑定 agent_id → 全生命周期归因
```

### 4.5 模块五：晒单与裂变

**对标 SVG 架构**：⑦ 晒单水群裂变

**核心机制**：赢钱截图 = 最强广告

| 功能 | 描述 |
|:---|:---|
| 一键晒单 | 交易盈利后，一键生成带收益率的海报 |
| 战绩分享 | 连胜/高收益自动生成分享卡片 |
| 排行榜 | 日榜/周榜/月榜，激发竞争 |
| 战队赛 | 组队 PK，队长拉人 = 自然裂变 |

**技术要点**：
- 海报在服务端生成（HTML → 图片），前端仅展示和触发分享
- 使用 Telegram 的 `shareToStory` 或直接发送图片到对话

## 五、轻量化技术架构方案

### 5.1 核心原则

> 不能有太多的 JS 和 CSS → 打开快 → 3 秒内完成首屏渲染

```
┌──────────────────────────────────────────┐
│           TG Mini App 客户端              │
│  ┌────────────────────────────────────┐  │
│  │  HTML (~15KB)                      │  │
│  │  - 语义化结构，无冗余节点           │  │
│  │  - 关键 CSS 内联（~10KB）          │  │
│  │  - 非关键 CSS 延迟加载             │  │
│  ├────────────────────────────────────┤  │
│  │  JS (~80KB gzipped)               │  │
│  │  - 原生 JS，无框架                 │  │
│  │  - 或 Preact (~3KB) 极轻量渲染    │  │
│  │  - 按页面懒加载模块               │  │
│  ├────────────────────────────────────┤  │
│  │  Assets (按需)                     │  │
│  │  - SVG 图标内联                    │  │
│  │  - 图片 CDN + WebP + 懒加载       │  │
│  │  - 字体使用系统默认               │  │
│  └────────────────────────────────────┘  │
│                                            │
│  ┌────────────────────────────────────┐  │
│  │  TG WebApp API 桥接层              │  │
│  │  - initData (用户信息)             │  │
│  │  - MainButton (TG 原生按钮)        │  │
│  │  - BackButton (TG 原生返回)        │  │
│  │  - HapticFeedback (触觉反馈)       │  │
│  │  - CloudStorage (本地缓存)         │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────┐
│           后端 API（厚服务端）             │
│  - 所有业务逻辑在服务端处理               │
│  - 前端仅负责渲染和数据展示               │
│  - API 响应精简，只返回必要字段           │
│  - 支持 ETag / 304 缓存                  │
└──────────────────────────────────────────┘
```

### 5.2 框架选型建议

| 方案 | 初始 JS 大小 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **原生 JS + 模块化** | ~5KB | 极致轻量，无依赖 | 开发效率低，状态管理需手动 |
| **Preact** | ~3KB | React 语法，生态兼容 | 需额外引入 |
| **Svelte** | ~0KB runtime | 编译时优化，无运行时 | 生态较小 |
| **SolidJS** | ~7KB | 性能极佳，细腻响应式 | 生态较小 |
| **Vanilla + Template Literals** | ~2KB | 最轻量 | 维护成本高 |

**推荐方案**：**Vanilla JS + 自定义轻量渲染层**

理由：
1. TG Mini App 页面数量有限（5-8 个页面），不需要完整路由框架
2. 交互模式固定（列表、表单、图表），可以抽象为极简组件
3. Telegram WebApp API 提供了原生 UI 组件（MainButton、BackButton、Popup），减少自定义 UI 需求
4. 开发团队可以封装一个 ~5KB 的微型渲染库，包含：
   - 模板字符串 → DOM 渲染
   - 简单的事件代理
   - fetch 封装 + 请求缓存
   - TG WebApp API 封装

### 5.3 页面拆分与懒加载

```
主入口 (index.html) ~15KB
├── 首页 (home.js) ~8KB      ← 首屏优先加载
├── 交易 (trade.js) ~15KB     ← 懒加载
├── 资产 (wallet.js) ~10KB    ← 懒加载
├── 任务 (tasks.js) ~8KB      ← 懒加载
├── 排行榜 (rank.js) ~8KB     ← 懒加载
├── 个人中心 (profile.js) ~10KB ← 懒加载
└── 共享 (common.js) ~10KB    ← 首屏加载（工具函数 + TG API 封装）
```

**总计首屏**：~33KB（HTML + CSS + common.js + home.js），gzip 后约 **12-15KB**

### 5.4 性能优化清单

| 优化项 | 方案 | 目标 |
|:---|:---|:---|
| HTML 内联关键 CSS | 首屏样式直接写在 `<style>` 标签中 | FCP < 1s |
| 无外部字体 | 使用 `system-ui` 字体栈 | 节省 50-100KB |
| SVG 内联 | 小图标直接内联 SVG，大图标用 CSS 绘制 | 减少 HTTP 请求 |
| API 响应精简 | 服务端只返回页面需要的字段 | 单次响应 < 5KB |
| 数据预加载 | 利用 `CloudStorage` 缓存不变数据 | 二次打开 < 1s |
| 图片策略 | WebP 格式 + CDN + 响应式尺寸 | 单图 < 20KB |
| 无重量级库 | 不引入图表库、动画库、UI 组件库 | 总 JS < 80KB |

## 七、风险与关键决策

### 7.1 关键风险

| 风险 | 影响 | 缓解措施 |
|:---|:---|:---|
| **TG 封号** | 主 Bot 被封 = 业务中断 | 三层冗余：马甲 Bot 热备 + 频道置顶位 + 多 Bot 分险 |
| **加载速度不达标** | 用户流失 | 严格资源预算，每阶段性能测试 |
| **合规风险** | 部分地区法律风险 | 合规牌照背书 + 分市场隔离 + 不碰法币 |
| **羊毛党攻击** | 红包/体验金被刷 | 复用现有风控体系：设备指纹 + 同频检测 + 提现门槛 |
| **代理刷单** | 佣金被套利 | 复用 V2 风控：盈亏结转 + 交易额门槛 + 人工审核 |

### 7.2 关键决策点

1. **托管钱包 vs 非托管钱包**：MVP 阶段建议托管钱包（用户体验优先），后期可选非托管
2. **自有渲染库 vs 轻量框架**：建议自研微型渲染库（~5KB），完全掌控资源大小
3. **红包 Bot 独立 vs 合并**：必须独立部署，隔离封号风险
4. **马甲 Bot 数量**：建议 3-5 个起步，每个市场至少 1 个备用
